# 非数値命令が別の横画へ影響する原因

2026-11-04。[前回の描画診断](DEPENDENCY-ENGINE-DIAGNOSTIC.md)で見つかった `hkcs_m28eb6@1` の出力差を、固定エンジン `@kurgm/kage-engine@0.7.0` の各調整段階で追跡した。[機械可読記録](invalid-command-adjustment-trace.json)に入力・関連エンジンファイルのSHA-256、調整値の差、出力SVGハッシュを保存した。

## 実データで観測した差

元の候補は末尾に非数値行 `s` を含む。これをメモリ上で省略した場合と比較すると、展開後のストロークindex 6（0始まり）の `urokoAdjustment` が、元データでは3、省略時は2だった。最初の差は `adjustUroko` で発生し、その後の `adjustUroko2`、`adjustKirikuchi` にも残った。他の調整値は一致した。SVGは異なるが、ポリゴン数は両方69。

## ソースで確認した経路

1. `kage.js` の `getEachStrokes` は `Math.floor(+columns[0])` で命令を数値化する。`s` はNaNになる。
2. `stroke.js` の `getControlSegments` は、このストロークについてNaNの座標を持つ線分を返す。
3. `2d.js` の `isCross` は、外積がNaNの場合に後方互換用の分岐でtrueを返す。診断でも、この不正ストロークが遠方の線分 `(1000,1000)–(1100,1000)` と交差すると判定された。
4. 明朝体の `adjustUroko` は他ストロークとの交差を調べ、横画端部の調整量を変える。そのため、不正行自身が輪郭を描かなくても、別の画の形状へ影響する。

これは固定バージョンの実装と計測に基づく原因説明であり、他のエンジンや現在のGlyphWiki全体の挙動へ一般化しない。エンジンソースは変更していない。

## 最小再現

```text
1:0:0:20:100:180:100
1:0:0:20:100:180:100$s
```

横画1本だけの前者は `urokoAdjustment=0`、非数値行を追加した後者は3となり、出力SVGも異なった。実データと最小例の両方を再実行し、診断JSONのバイト一致を確認した。

```text
node tools/trace_invalid_command_effect.mjs diagnostic-bundles.json trace.json
```

入力bundleの生成は [依存診断の手順](DEPENDENCY-ENGINE-DIAGNOSTIC.md)を使う。トレースは処理を包んで調整値を記録するだけで、元の処理結果を変更しない。

## データセットでの扱い

不正行を「描かれないので無害」とみなさず、依存問題の状態を維持する。通常の描画処理はこのbundleを拒否し、診断だけを分離する。問題行を推測して削除したKAGEを正本として配布しない。元の作者が意図した形、修正すべきデータ、典拠字形との一致は、この原因特定だけでは確定しない。
