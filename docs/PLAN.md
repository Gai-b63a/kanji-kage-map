# 実装計画

2026-11-04策定。段階1の取得・台帳CLIは実装・全件実行済みです。段階2の公式dump索引・候補収集・個別依存解決も実装しました。[台帳監査](INVENTORY-AUDIT.md)と[GlyphWiki監査](GLYPHWIKI-AUDIT.md)を参照してください。全候補の閉包監査、固定入力からの別環境再生成、GitHubでの初回配布版公開・取得検証まで実施済みです。字形レビューと未解決対応の調査は継続中です。以下は完了条件を含む全体計画です。

## 1. 原本固定と全件台帳

最初の実装単位はPython標準ライブラリを中心とした取得・台帳CLIと小さな検証用入力です。大規模なDBや描画エンジンはまだ不要です。

1. `sources.lock.json` に原URL、最終URL、提供元、資料版、取得UTC日時、バイト数、SHA-256、文字コード、ライセンス参照と確認状態を記録する。原本は `data/raw/` に保存しGitから除外する。Web検索の整形テキストのハッシュを原本ハッシュにしない。
2. BabelStone `IDS.TXT`、`IDS_PUA.TXT`、PUAページの対象表・番号付き部品説明を突き合わせる。見出しだけでなく、全IDSの葉、説明内の部品、IDS空欄のPUA行も台帳化する。表だけにある項目とTXTだけにある項目は消さず差分にする。
3. Unicode採用版は版付きUCDの実体・ReadMe・権利表示を取得して確定する。漢字集合は `Unified_Ideograph` と、割当済みの互換漢字を含める。部品集合は割当済みのCJK部首補助、康熙部首、CJK筆画、およびBabelStone内のUnicode部品を含め、種別を分ける。未割当のブロック穴を文字として数えない。追加の漢字関連記号は別分類で保持し、勝手に捨てない。
4. IDS演算子、地域ラベル、変異指示、構文記号を部品と誤認しない。`？` は未知部品の出現記録とし、同一字形の共通識別子にしない。番号付き部品はIDS原本の版を含むIDとし、PUA表との関係は根拠付きの別レコードにする。
5. `inventory.jsonl`、`occurrences.jsonl`、`source-differences.json`、`parse-issues.jsonl` を生成する。Unicode集合をU、BabelStoneのUnicode見出し集合をBとして U∩B、U−B、B−Uを出力する。部品とPUAは別母数を併記する。

完了条件：全原本行が採用・注記・解析課題のいずれかに説明され、重複・空欄・未解析を集計する。公称件数と実測の相違を報告する。同じ原本で同じソート済み出力を再生成できる。BOM、補助面文字、複数IDS、番号付き部品、未知部品、空欄PUA、Unicode範囲境界・互換漢字のテストが通る。

実装済みCLI：`python -m kanji_kage_map acquire --manifest sources.json` → `python -m kanji_kage_map inventory --lock sources.lock.json`。既存lockの入力復元には `restore --lock sources.lock.json` を使います。

## 2. 既存対応候補と参照の調査

- 公式dumpを版固定して索引化する。既存試作DBは必要なときだけ明示パスでread-only接続し、サンプル照合する。試作の取り込み処理が捨てた列・行も調べ、原本の代替と断定しない。
- Unicode名、地域接尾辞・異体字名、別名参照、典拠識別子に基づく候補を列挙する。命名規則の実体を公式資料とdumpで確認してから規則化する。
- `candidates.jsonl` に取得規則、候補の棄却理由、原本の位置を保存する。字形一致のない機械的候補を `matched` にしない。
- グリフは `(snapshot_id, name, revision)` を識別キーとし、原KAGEを無改変で保持。無版参照は同じsnapshot内の版へ固定し、明示 `@版` を最新へ置換しない。版が特定できなければ `revision_unresolved` とする。
- 依存辺には親グリフ・KAGE行番号・生参照名・解決先を保存する。非恒等の単一参照を単なる別名として潰さない。

完了条件：全台帳IDに候補調査状態がある。再帰参照切れ・循環・不正データ・資源上限による中断を区別する。候補なしでも台帳から消えない。

## 3. 例外・PUAの対応

- `provider + source_version + local_id` をPUAのキーとする。符号位置の一致だけで結合しない。
- 番号付き部品の説明、PUAの原典・IRG等の出典ID、符号化移行先、GlyphWikiの典拠を照合し、別名・地域差を調査する。IDSが似ていることは補助証拠に留める。
- 手動対応は `overrides.jsonl` に根拠URL・資料位置・比較対象版・レビュー者・日時を記録する。複数候補を保持し、選択条件を明示する。
- 孤立部品と完成字形内の変形部品、包含される部品と字形全体を区別する。近似字形は一致として数えない。

完了条件：全PUA・例外に未調査／候補／確認済み／曖昧／欠落の状態と根拠または次の調査事項がある。未解決を残したリリースは可能だが「全件対応」と称さない。

## 4. 検証とレビュー

- 自動：ID一意性、参照整合性、原本ハッシュ、版固定、全依存閉包、KAGE構文、循環・欠落を全件検査する。描画する場合はエンジン版を固定し、有限座標・空出力・例外を記録する。
- 目視：典拠字形と候補を同条件で比較する。PUA、地域差、複数候補、近似は優先する。レビューしていない項目を標本結果から確認済みに昇格しない。
- 対応状態と `dependency_status`、`render_status`、`review_status` を独立保持する。未対応命令があっても原KAGEを捨てない。
- `coverage.json` はUnicode漢字、Unicode部品、BabelStone見出し、番号付き部品、PUAを分母別に集計。複数の集合に属する項目を総数で二重計上しない。候補率・確認済み率・依存解決率を分ける。

完了条件：全件検査のログ、レビュー範囲、残課題、数え方が揃う。意図的に壊した版参照・循環・PUA衝突を検出できる。

## 5. 再現可能な公開

- 台帳、対応表、グリフ、依存辺、根拠、未解決一覧、スキーマ、出典ロック、件数監査をリリース単位で固定する。JSONLを正本とし、必要ならSQLiteを派生成果物として配布する。
- 依存データを含むKAGE bundleの配布条件を確認し、同梱するライセンス・NOTICEを作る。フォント、IDS、GlyphWikiデータ、エンジン、独自コードを分けて扱う。
- オフライン再生成とハッシュ照合を確認する。CIは小規模fixtureで通常検査し、全件監査は固定入力を使用する明示的なジョブに分ける。
- 大容量原本をGitに入れず、取得手順・検証ハッシュと必要な配布先を記載する。上流更新で旧版原本を再取得できない場合も再現性の制限として明示する。
- GitHubリポジトリ、CI、タグ、Releaseを実際に確認して初めて公開済みと報告する。

完了条件：別環境で固定入力から再生成でき、公開URL・配布物・チェックサムが一致する。未解決項目を利用者が取得・判別できる。

## 最小データ契約（実装時にJSON Schema化）

| レコード | 必須情報 |
| --- | --- |
| source | source_id、版、URL、取得日時、原本SHA-256、ライセンス状態 |
| inventory | entity_id、提供元、版、元ID、種別、Unicode属性、所属集合、出典位置 |
| occurrence | entity_id、資料行、IDS別形・地域ラベル、出現位置、原トークン |
| mapping | entity_id、候補配列、対応状態、採否理由、字形差、証拠ID、確認情報 |
| glyph | snapshot_id、name、revision、原KAGE、KAGEハッシュ |
| dependency | 親glyph、行番号、raw_ref、解決先glyph、解決状態 |
| evidence | 資料版、URL／原本位置、判断、レビュー者・日時 |
